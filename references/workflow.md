# 执行与证据契约

## 工作区

所有项目产物写入用户题目目录，技能与模板原件只读。按需建立：

```text
state/project.json
rules.md
team_plan.md
ai_usage.md
data/                 输入原件只读
code/                 队伍代码与允许的辅助处理
results/              结果及运行记录
figures/              图及对应数据
evidence.csv
paper/                论文源文件
checks/               核验记录
checkpoints/          已验证版本
submission/           最终候选文件
```

## 状态记录

`project.json` 记录 `schema_version`、`competition`、`season`、`identity_status`、`rules_checked_at`、`deadline`（含时区）、`stage`、`per_question`、`decisions`、`artifacts`、`checks`、`next_action`。未知值用null，不用猜测补齐。决策同时记录提出者、原因与证据。

每个artifact保存path、sha256、输入依赖、生成时间和status；每个check保存检查者、检查时间、输入哈希、方法、结果和问题。恢复时核对磁盘实际文件和哈希，不能仅凭旧PASS继续。状态写到同目录临时文件后原子替换；不要清空已有状态。

## 子问题最小闭环

队员方案 → 输入与单位核对 → 队员运行代码 → 结果与约束核对 → 队员解释 → 图与证据记录。每一步明确来源，不把AI建议记成队员已确认。

一次运行记录输入文件SHA-256、代码版本或哈希、命令与工作目录、随机种子、关键参数、依赖版本、退出码、输出文件。随机过程需要记录队伍选择的重复运行方案；结果不能仅留在聊天里。

证据表字段：claim_id、question、paper_location、result_path、result_key、raw_value、unit、display_precision、display_value、run_command、artifact_hash、team_reviewer、status。逐项核对单位、统计口径和舍入；0.1234显示为12.34%需要记录换算。没有证据的结论标记待补，不编造。

预测检查是否存在数据泄漏、验证划分与基线；优化核对可行性、约束残差、求解状态和最优性声明依据；评价核对指标方向、归一化、权重来源。整理发现交给队伍决定核心修正，不替队伍创造研究结论。

## 四个检查节点

| 节点 | 可核验的退出条件 |
|---|---|
| 规则模板 | 届次确认、规则有来源、官方模板副本成功导出；未确认项单列 |
| 最小结果 | 当前子问题代码运行、输出存在、单位及约束由队员核验 |
| 证据大纲 | 核心主张逐项对应结果字段和队员论证；缺项不进入成稿结论 |
| 最终文件 | 冻结版本重新导出、数值与引用检查、逐页视觉审查、披露及提交文件核对 |

这不是四次全量审计。单阶段只验相关节点；修改哪个输入，就复验受影响的节点。没有子代理时可记录主代理检查和队员复核，两者不可冒称独立代理审核。

## 时间与交付

建议比赛前12小时走通一次模板导出；约60—78小时保留覆盖全题的完整V1；距竞赛结束6小时冻结研究，处理影响可读性、准确性和提交的必要问题。这些是内部建议，可随队伍实际进展调整。

V1只读保留。改动在新副本进行；新版本失败可回退。编译通过仅代表导出成功，还需逐页看公式、图、表、目录和分页。申报已提交需队员或平台回执证据。
